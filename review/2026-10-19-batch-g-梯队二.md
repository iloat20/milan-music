# 批次 G 执行记录：第二梯队（预测式返回）

基线：批次 F 之后、未发版。用户明确排除「通知栏 ±10s / 收藏按钮」，本批次不含 Media3 自定义通知。

结论：**只有预测式返回（Predictive Back）可以安全落地**。第二梯队另外两项——音效链与共享元素过渡——都卡在「必须先做产品决策」上，本批没有动，理由见后两节。

## 一、已完成：预测式返回

| 项 | 内容 |
|---|---|
| 文件 | `ui/player/PlayerScreen.kt` |
| 替换 | `BackHandler { dismissToHome() }` → `PredictiveBackHandler { ... }` |
| 依赖 | `androidx.activity:activity-compose 1.13.0` 已内置，无需新增 |

### 实现要点

系统返回手势的进度直接喂给现有的 `offsetY` Animatable —— 也就是下滑关闭用的那个值。播放页的位移、缩放、透明度都从 `offsetY` 派生，所以跟手预览不需要第二套动画。

```kotlin
PredictiveBackHandler { progress ->
    if (isSettling.value) return@PredictiveBackHandler
    try {
        progress.collect { event ->
            val isIntermediate = event.progress > 0f && event.progress < 1f
            if (isIntermediate) offsetY.snapTo(event.progress * sheetHeightPx.floatValue)
        }
    } catch (cancellation: CancellationException) {
        offsetY.animateTo(0f, spring(stiffness = Spring.StiffnessMediumLow))
        throw cancellation
    }
    dismissToHome()
}
```

### 为什么不按 SDK 版本分支

第一版写的是 `if (SDK_INT >= 34) snapTo(...)`，随后改成判断进度值本身。原因：`SDK_INT` 是**对平台行为的假设**，而 `event.progress` 是**观测到的数据**。不支持预览的版本只上报一个 `1.0` 事件，按值判断天然跳过 snap，行为与旧 `BackHandler` 完全一致；支持预览的版本有中间值，自然跟手。将来平台把预览下放到更低版本，这段代码不需要改。

这条对 API 26–33 是硬保证：**它们走的仍是原来那条 240 ms 滑出动画**，不会因为这次改动变成瞬间消失。

### 保留的两个既有约束

1. `enabled` 不绑定 `isSettling`。原注释已经记录过原因：取消注册会让第二次返回键穿透到 Activity 默认处理，直接退出应用。守卫放在回调内部（`if (isSettling.value) return`）。
2. `sheetHeightPx` 尚未测量时为 0，`progress * 0 = 0`，位移不生效但不会崩；flow 完成后仍走 `dismissToHome()` 正常关闭。

## 二、未做：音效链（需要新界面）

`Equalizer` / `BassBoost` / `Virtualizer` / `LoudnessEnhancer` / `DynamicsProcessing` 全部挂在 `player.audioSessionId` 上，技术上没有障碍。卡点不在技术，在**入口**：

当前应用没有任何设置页。曲库顶栏只有一个排序 `DropdownMenu`（`HomeScreen.kt:221`），播放页底部只有喜欢、进度条、播放控制四项。EQ 必须有一个入口，而入口位置、面板形态、是否给预设、是否与 offload 互斥切换——这些是产品决策，不是实现细节。

另有一个必须先解决的冲突：**offload 与音效互斥**。批次 F 打开了 `AUDIO_OFFLOAD_MODE_ENABLED`，而卸载路径绕过 ExoPlayer 的音频后处理。EQ 生效时必须把模式切回 `DISABLED`，关闭 EQ 时再切回。这个切换对用户是否可见（比如"开音效会更费电"的提示），也需要定。

三个候选形态：

| 方案 | 形态 | 成本 | 隐患 |
|---|---|---|---|
| A | 播放页底部加图标，点开底部升起 EQ 面板 | 中 | 播放页已有封面（52% 高度）+ 四行控件，纵向空间紧张 |
| B | 顶栏加设置入口 → 全屏设置页 → 音效分组 | 中高 | 新页面，但 ReplayGain 等其他开关也有地方放 |
| C | 只做「低音增强 开/关」二态，不做面板 | 低 | 不算 EQ，用户预期可能落空 |

倾向 B：ReplayGain（批次 F 因无开关入口而搁置）也正好需要这个位置，一次投入解决两个待办。

## 三、未做：共享元素过渡（与现有架构冲突）

`SharedTransitionLayout` 在技术上能接，但和播放页现在的进出场方式打架：

- 进场是 `AnimatedVisibility` + `slideInVertically`（`MilanApp.kt:38-47`），**整页**从底部滑入；
- 共享元素要求封面从迷你播放器位置 `sharedBounds` 飞到播放页封面位。

两者同时跑，封面会同时被"整页位移"和"bounds 插值"驱动，画面会抖。要做得对，只能二选一：把进场从"上滑"改成"背景淡入 + 封面飞行"，这是**重新定义播放页的进出场动效**，属于视觉设计决策。

而且关闭路径也是障碍：现在的下滑关闭是手势驱动的 `offsetY`，而 `sharedBounds` 的返回动画由 transition 驱动，两者不能在同一个手势里平滑交接。

三个候选：

| 方案 | 做法 | 成本 | 代价 |
|---|---|---|---|
| A | 保持现状，不做共享元素 | 0 | 无 |
| B | 进场改为「背景淡入 + 封面飞行」，关闭仍用滑出 | 高（需把 SharedTransitionScope 传进 HomeScreen 的迷你播放器） | 进出场语义不对称 |
| C | 整页仍上滑，封面额外做 scale 0.92→1 + fade | 低 | 不是真正的共享元素，视觉提升有限 |

倾向 A：当前的上滑 + 跟手下滑是自洽的，共享元素换不来同等收益。
