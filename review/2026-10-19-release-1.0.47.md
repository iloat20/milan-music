### 1. 位图缓存回收出口

`LruCache` 只在 `put()` 超限时驱逐，从不主动缩容——用户浏览一遍大曲库、切后台熄屏听歌，24 MB 列表缓存仍钉在堆里。现在 `Application.onTrimMemory` 在 `UI_HIDDEN` 缩到 1/6、`BACKGROUND` 及以上全清；通知封面缓存由 `PlaybackService.onTrimMemory` 单独管（loader 由 Service 私有持有，Application 够不到）。

**注意**：`TRIM_MEMORY_*` 在 API 37 上大面积弃用（反编译 `platforms/android-37.0/android.jar` 的 `ComponentCallbacks2` 确认 `COMPLETE / MODERATE / RUNNING_*` 均标 `Deprecated: true`，只有 `UI_HIDDEN`(20) 与 `BACKGROUND`(40) 仍下发）。实现按开放区间写，兼容老机型仍下发的 60/80。

### 2. 进度轮询订阅门控

原先"播放即起、暂停即停"，但 `progress` 的唯一消费者是播放页；息屏时无人订阅，循环仍每 500 ms 在主线程唤醒一次，CPU 进不了深 C-state。现在加第二道闸：`subscriptionCount > 0` 才跑。

### 5. MediaStore 扫描水位线

`COUNT(*)` + `MAX(DATE_MODIFIED)` 聚合与缓存快照比对，命中即跳过全量扫描。provider 拒绝聚合投影时 `runCatching` 返 null 并回落全量扫描，不会误判为空库。

### 9. Haze 模糊输入降采样

`LocalHazePerformanceMode = Performance`，一个 provider 覆盖全部玻璃面板。`Balanced` → `Performance` 是 0.79 → 0.5 线性（62.5% → 25% 像素）。**半径随缩放同步缩**，观感半径不变。唯一可能的可见差异是 0.03 噪声颗粒放大 2 倍。

### mapping + 反汇编（M1 / M2）

R8 会重命名 `haze` 与自定义类，直接在 dex 里搜类名没有意义。用 `mapping.txt` 反查：

```
com.milan.music.ui.theme.ThemeKt -> eu2:
dev.chrisbanes.haze.HazePerformanceMode$Companion -> dq0:   (Performance -> c)
dev.chrisbanes.haze.HazePerformanceModeKt -> gq0:            (LocalHazePerformanceMode -> a)
```

`apkanalyzer dex code --class eu2` 输出中 `.line 154` – `.line 167` 区间：

```
sget-object v5, Lgq0;->a:Lvv;        // LocalHazePerformanceMode
sget-object v7, Ldq0;->c:Leq0;       // HazePerformanceMode.Companion.Performance
invoke-virtual {v5, v7}, Lvv;->a(Ljava/lang/Object;)Lg62;   // ProvidableCompositionLocal.provides
filled-new-array {v3, v5}, [Lg62;   // → CompositionLocalProvider
```

源码行号（`.line 154` / `.line 161` / `.line 163`）与 `Theme.kt` 完全对应，即 M2 确实进了 release 包。

M1 由 `mapping.txt` 直接证实：

```

    12:15: ArtworkRepository.evictAll():160 -> onTrimMemory
```

## 尚未验证（需真机，优先级从高到低）

1. **进度条**（P1 唯一有回归风险处）：播放页 500 ms 刷新、暂停后位置不跳变、sheet 关掉再开立即回位。
2. **后台内存**：浏览 300 首 → Home 键 → `dumpsys meminfo com.milan.music`，期望 −25～30 MB。
3. **trim 三档是否真的缩**：`adb shell am send-trim-memory com.milan.music RUNNING_LOW` / `UI_HIDDEN` / `BACKGROUND`。
4. **息屏功耗**：`batterystats --reset` + 息屏 30 min + `--charged`，期望 `wakeups` 从约 3600 降到接近 0。
5. **二次冷启动**：`am start -W` 对比首次与第二次的 `TotalTime`，期望第二次明显更低。
6. **小组件**：双实例（不同宽度）圆角是否正确；无实例时 `refresh()` 不应触发广播。
7. **崩溃路径**：连续切换曲目 50 次不崩（M6 修的是 `getPixels` 在 HARDWARE 位图上的异常穿透）。
8. **颗粒感**：迷你播放器 / 底部栏 / 排序菜单的噪声颗粒是否可见。可见就改 `Fixed(0.35f)`。
9. **offload**（1.0.46 遗留）：`dumpsys media.audio_flinger | grep -i offload`，仍未验证。

## 已知遗留

- **P2 不做**：`hazeSource` 给每个源节点建全尺寸离屏层且每帧无条件重录，本屏两个源约 20.7 MB。但去掉任一源都会让玻璃面板退化成"磨砂渐变"，属产品决策而非优化项（`review/2026-10-19-m2-haze-performance-mode.md` 第 5 节）。
- **M3 保留**：播放页 `blur(48.dp)` 背板，批次 B 已复核保留，本轮仅补充了"离屏缓冲显存"这一角度，未推翻。
- **M4 待实测**：曲库 3000+ 首时 `setMediaItems` 是否撞 Binder 1 MB 事务上限。
- 与 1.0.46 一致：ReplayGain / EQ 未做；`store/screenshots/01-library.jpg` 与真实界面不一致，上架前必须重拍。
