# 64 位（arm64-v8a）打包审计 — milan-music 1.0.48

审计对象：`app/build/outputs/apk/release/app-release.apk`、`app/build/outputs/bundle/release/app-release.aab`
构建配置：`app/build.gradle.kts` → `release { ndk { abiFilters += "arm64-v8a" } }`
结论：**PASS**。全部 105 个运行时依赖中仅 2 个含原生库，均提供 arm64-v8a；成品 APK/AAB 内只有 AArch64 ELF，且满足 16 KB 页要求。

## 1. 结论表

| 检查项 | 结果 | 证据 |
| --- | --- | --- |
| release 运行时依赖总数 | 105 | `releaseRuntimeClasspath` 解析结果 |
| 其中含 `jni/` 原生库 | **2** | 其余 103 个为纯 JVM/AAR 无原生代码 |
| 含原生库但缺 arm64-v8a | **0** | 逐包 `jni/` 目录比对 |
| APK 内 `lib/<abi>/` 目录 | `arm64-v8a` 唯一 | 目录枚举 |
| APK 内 ELF 对象 | 2 个，全部 64-bit AArch64 | 解析 ELF header `e_ident[EI_CLASS]`=2、`e_machine`=183 |
| APK 内 32 位 ELF | 0 个 | 全条目 ELF magic 扫描（不止 `lib/`） |
| AAB 内原生库路径 | `base/lib/arm64-v8a/` 唯一 | 目录枚举 |
| `.so` 存储方式 | `STORED`（未压缩） | zip 条目压缩方法 |
| `.so` 16 KB 页对齐 | 对齐 | `zipalign -c -P 16 -v 4` → `(OK)` |
| ELF 加载段 16 KB 兼容 | 是 | 全部 `PT_LOAD` 的 `p_align = 0x4000` |
| 仓库内自建 `jniLibs` | 无 | `app/src/main/jniLibs` 不存在 |
| `uses-native-library` 依赖声明 | 无 | `AndroidManifest.xml` 无该标签 |

## 2. 第三方原生依赖矩阵

| 坐标 | 打包文件 | 提供的 ABI | 结论 |
| --- | --- | --- | --- |
| `androidx.graphics:graphics-path:1.0.1` | `libandroidx.graphics.path.so` | arm64-v8a, armeabi-v7a, x86, x86_64 | ✅ 含 arm64-v8a |
| `androidx.datastore:datastore-core-android:1.2.1` | `libdatastore_shared_counter.so` | arm64-v8a, armeabi-v7a, x86, x86_64 | ✅ 含 arm64-v8a |

**这是全部原生依赖，不是抽样。** 其余 103 个运行时产物（Compose BOM 全家桶、Media3 exoplayer/session/common、Haze、kotlinx-serialization、lifecycle 等）压缩包内没有任何 `jni/` 目录，也没有任何 `.so` 落在 `jni/` 之外（如 `assets/`、`lib/` 根）——后一条单独扫过，因为 `abiFilters` 只过滤 `jni/` 派生的 `lib/<abi>/` 路径，藏在 assets 里的 `.so` 不会被过滤，也不会被这里的手段发现，所以必须提前确认不存在。

> 注：Media3 本身不含原生库。项目未引入 `media3-decoder-ffmpeg` 之类的扩展，因此不存在「ExoPlayer 带 ffmpeg 二进制」这一常见误解路径。

## 3. 复现命令

```bash
# 1) 列出 release 运行时全部产物（含传递依赖）
cat > /tmp/list-cp.gradle << 'EOF'
gradle.projectsEvaluated {
    def app = gradle.rootProject.findProject(':app')
    app.tasks.register('printReleaseRuntimeClasspath') {
        doLast {
            app.configurations.getByName('releaseRuntimeClasspath').resolvedConfiguration
                .resolvedArtifacts.each { a ->
                    def id = a.moduleVersion.id
                    println "ART\t${id.group}:${id.name}:${id.version}\t${a.file.name}\t${a.file.absolutePath}"
                }
        }
    }
}
EOF
./gradlew -I /tmp/list-cp.gradle :app:printReleaseRuntimeClasspath --offline -q | grep ^ART

# 2) 逐包检查 jni/ 下的 ABI 目录（任一缺 arm64-v8a 即失败）
#    见 build/abi_scan.py（gitignored，构建目录内，可直接复用）

# 3) 成品包：ABI 目录 + ELF 位宽/机器类型 + 16 KB 页对齐
unzip -l app/build/outputs/apk/release/app-release.apk | grep "lib/"
"$ANDROID_HOME/build-tools/37.0.0/aapt2" dump badging \
    app/build/outputs/apk/release/app-release.apk | grep native-code
"$ANDROID_HOME/build-tools/37.0.0/zipalign" -c -P 16 -v 4 \
    app/build/outputs/apk/release/app-release.apk | grep -E "\.so|Verification"
```

`aapt2` 输出：`native-code: 'arm64-v8a'`
`zipalign` 输出：两个 `.so` 均 `(OK)`，`Verification successful`

## 4. 体积与内容核对

| 指标 | 多 ABI（旧 dist 包） | 仅 arm64（本次） | 差值 |
| --- | --- | --- | --- |
| APK 字节数 | 2,477,875 | 2,379,987 | −97,888 |
| 解压后总字节 | 4,374,731 | 4,321,219 | −53,512 |
| `lib/` 条目数 | 8 | 2 | −6 |
| `classes.dex` | 3,808,120 | 3,809,428 | +1,308（本次阻断项修复） |
| `resources.arsc` | 231,344 | 231,344 | 0 |

条目集合对比：除 6 个被过滤的 `.so` 外两个包完全一致。压缩后少 97,888 B 而解压后只少 53,512 B，差额来自 16 KB 页对齐 padding——被移除的 6 个 `.so` 原本各自占满一个 16 KB 页，连同 padding 一起消失。

## 5. 残余风险

1. **32 位设备不可安装**。armeabi-v7a 已从 release 移除，minSdk 26 的纯 32 位设备无法安装。这是「严格 64 位」的必然代价，属已知取舍。
2. **未来依赖可能引入无 arm64 的原生库**。`abiFilters` 只能过滤、不能补齐：一旦某个新依赖只提供 armeabi-v7a，过滤结果是「该依赖的原生库整体消失」，表现为运行时 `UnsatisfiedLinkError` 而不是构建失败。当前审计是人工一次性执行，没有构建期守卫。
3. **debug 仍是 4 ABI**。按上一轮确认的范围，`abiFilters` 只在 `release` 生效；若将来要求 debug 也严格 64 位，需移到 `defaultConfig`，代价是 x86 模拟器不可用。
4. **AAB 侧已同规则生效**（`base/lib/arm64-v8a` 唯一），但 Play 的分发取决于上传产物；若上传旧的 4-ABI AAB，上述结论不适用。

第 2 条建议用构建期守卫兜住（示例形态：一个 `check` 依赖的 Gradle 任务，扫描合并后的原生库目录，遇到非 AArch64 或缺失 ABI 直接 fail）。是否要加，等你确认。
