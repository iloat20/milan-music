# 1.0.85（b86 / 2026-10-27）

本批修掉全仓审查发现的两处缺陷，把依赖推到最新稳定版，并接入应用级 baseline profile
的采集基础设施。三处行为变化都需要真机确认，未在打包前验证。

## 改动

### 1. 进度条左端在位置 0 时显示 `--:--`

`ui/util/Format.kt` 原来只有一个 `formatDuration`，`<= 0` 一律判为"未知"。播放位置在
每首歌开头、拖到最左、在 0 处暂停时恰好是 0，左端标签因此显示 `--:--`，读起来像
"这首歌没有进度"；无障碍的 `stateDescription` 同样错。

拆成两个语义入口：`formatDuration`（0 = 还不知道）与 `formatPosition`（0 = 合法位置，
输出 `0:00`），时钟格式化下沉为私有 `formatClock`。调用点 `PlayerScreen.kt:864`
（无障碍描述）与 `:978`（可见标签）改用后者。

### 2. 快速滚动后个别封面永久停在占位图

`MemoCache` 的等待方拿到 `null` 只重读一次 `peek` 就交出去，而列表封面的解码
（`ArtworkRepository.load`）不在 `NonCancellable` 里：A 行滚出屏幕取消了生产者 →
同屏仍在等待的 B 行收到 `null` → 被当成"这张专辑没有封面" → `CoverArt` 的
`LaunchedEffect(albumId)` key 没变、不会重试 → 那一行一直停在占位图，直到滚出去再
滚回来。播放页那条不中招（解码跑在 `NonCancellable` 里）。

改为区分「结论」与「无结论」：`Outcome.Done`（这个 key 确实没有值）与
`Outcome.Abandoned`（生产者被取消）。后者重读 `peek`，仍无则由等待方接手生产，
最多 3 次。

### 3. datastore 1.2.1 → 1.3.0

14 项依赖里唯一有升级空间的一项（2026-10-21 发布）。release notes 全是新增能力
（Web 存储、tink 加密、tracing、`DataStore.Builder` 转 public、自带 baseline profile），
无破坏性变更；POM 仍钉 coroutines 1.9.0，不会悄悄抬高运行时版本。代价 +16 B。

其余 13 项上游稳定版就是现用值：AGP 9.5 / Kotlin 2.5 / media3 1.12 都还只有
rc / beta / alpha，不动。

### 4. 应用级 baseline profile 基础设施

此前包内 `assets/dexopt/baseline.prof` 全部来自依赖（Compose、media3、datastore
各带一份），我们自己的启动路径（`MilanMusicApp` → `MainActivity` → 曲库恢复 →
首页首帧）没有一条规则，冷启动那段只能现场 JIT。

新增 `:baselineprofile`（`com.android.test`）模块 + `androidx.baselineprofile` 1.5.0
插件；`BaselineProfileRule` 只采冷启动（播放路径依赖媒体文件与 MediaSession，采集时
不稳定，且会把 profile 预算花在只在播放时才热的代码上）。

采集命令：`./gradlew :app:generateReleaseBaselineProfile`，结果写回
`app/src/release/generated/baselineProfiles/`，随下次构建进包。

**本批未采集**：这台机器的 BIOS 关闭了虚拟化（`VirtualizationFirmwareEnabled: False`、
`HypervisorPresent: False`），x86 模拟器无法加速，也没有连接真机。任务链已实测——
无设备时 `:baselineprofile:connectedNonMinifiedReleaseAndroidTest` 明确报
`No connected devices!` 并失败，不会产出一个空 profile。所以这次发布的
`baseline.prof` 仍是依赖合并的那份。

## 仍需真机确认

1. 拖到最左端松手：左端应显示 `0:00`，不是 `--:--`。
2. 快速上下甩动列表后停住：不应有行停在占位图；若仍有，说明接手机制在真实滚动节奏下
   不够，需要考虑把列表解码也纳入 `NonCancellable`。
3. datastore 1.3.0：曲库缓存恢复、播放快照（队列 + 位置）、损坏文件恢复三条路径。
   单测覆盖不到它的真机行为。
4. baseline profile 采集：接一台设备跑 `generateReleaseBaselineProfile`，确认
   `app/src/release/generated/baselineProfiles/` 出现规则文件、`baseline.prof` 明显变大；
   再用 macrobenchmark 量冷启动，确认收益。
