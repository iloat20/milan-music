## 本版内容

| # | 改动 | 文件 | 用户可感知 |
|---|---|---|---|
| 1 | 音频卸载（offload）+ 强制 gapless | `play/PlaybackService.kt` | 息屏播放功耗、专辑曲间无缝 |
| 2 | 小组件封面圆角跨版本修复 | `widget/MusicWidgetProvider.kt` | Android 8–11 封面不再直角 |
| 3 | 预测式返回 | `ui/player/PlayerScreen.kt` | 返回手势跟手预览播放页下滑关闭 |

另外 1.0.45 遗留的两处改动（搜索框去占位文案、图标 21 dp）也在本包内。

### 1. 音频卸载

`TrackSelectionParameters` 上启用 `AUDIO_OFFLOAD_MODE_ENABLED` 并要求
`setIsGaplessSupportRequired(true)`。注意 Media3 1.11 已删除
`DefaultRenderersFactory.setEnableAudioOffload()`，只能走 `TrackSelectionParameters`。

选择 `ENABLED` 而非 `REQUIRED`：后者在不支持硬件卸载的设备上会直接拒绝播放。

**收益口径**：`WAKE_MODE_LOCAL` 仍持有 partial wake lock，CPU 不允许深睡，
所以收益是"CPU 不再逐帧解码"，不是"CPU 进入低功耗态"。社区流传的 200–300 mA → 50–100 mA
是无 wake lock 场景的数据，**不能用于发布文案**。

### 2. 小组件圆角

在 app 进程内用 Canvas `drawRoundRect` + `PorterDuff.SRC_IN` 预裁封面位图，
半径按 `getAppWidgetOptions` 读到的真实卡片宽度换算。原先的 `clipToOutline` 在 API 26–30
上需反射且方法名不在 RemoteViews 白名单，调用会让整个挂件加载失败。

### 3. 预测式返回

`BackHandler` → `PredictiveBackHandler`，系统手势进度直接喂给下滑关闭用的 `offsetY`。
按 `event.progress` 的**值**判断是否中间态，而不是按 `SDK_INT` 分支——不支持预览的版本
只上报 `1.0`，天然跳过 snap，API 26–33 仍是原来的 240 ms 滑出。

## 内容核验（为什么本包确实包含上面的改动）

R8 混淆了 media3 的类名，在 dex 里直接搜 `AudioOffloadPreferences` 会得到 0 命中，这是正常现象。
用 `mapping.txt` 反查才是可靠证据：

```
androidx.media3.common.TrackSelectionParameters$AudioOffloadPreferences -> tv2
androidx.media3.exoplayer.DefaultRenderersFactory -> e40
```

反汇编 `classes.dex` 后：

- `PlaybackService.onCreate` 内 `new-instance v1, Le40;` + `<init>(Lcom/milan/music/play/PlaybackService;)V`
  —— 即 `DefaultRenderersFactory(this)`；
- `Ltv2;` 全 dex 96 处引用，含 `Lvv2;.w:Ltv2;`（`TrackSelectionParameters.audioOffloadPreferences` 字段）。

**体积巧合，不是未重建**：1.0.44 / 1.0.45 / 1.0.46 三个包的 APK 总字节数都是 2,477,875 B。
但本轮 `classes.dex` 从 3,798,816 → 3,802,004（+3,188 B），`AndroidManifest.xml` CRC 变化，
SHA-256 不同。总大小相同是 zip 压缩吸收了 dex 增量，**体积不能作为"未重建"的判断依据**。

## 尚未验证（需真机，优先级从高到低）

1. **offload 是否真的生效**：`adb shell dumpsys media.audio_flinger | grep -i offload`。
   看不到 offload 线程就说明这套配置在该机型上是白改。
2. **息屏功耗实际降幅**：必须自己测，不能引用社区数字。
3. **API 26–33 返回键是否仍为 240 ms 滑出**：这是本轮最容易出回归的一条。
4. **API 26–30 小组件圆角**：本轮的修复目标版本，恰恰没有设备。
5. gapless 实测（挑现场 / 古典专辑，软件与卸载两条路径分别验）。
6. 连续两次返回键不退出应用。
7. offload 下 seek 延迟（通常 100–200 ms，注意进度条回弹错觉）。
