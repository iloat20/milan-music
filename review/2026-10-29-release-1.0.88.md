# 1.0.88（b89 / 2026-10-29）

**这一版没有任何运行时改动。** 改的是「一个断言能证明什么」：新增生成式输入测试、变异率与
APK 逐条目对比三件取证物，并把「哪些结论有读数、哪些没有」写成台账。`classes.dex` 与
1.0.87 相比只差 26 字节，全部是版本字符串与 dex 头部校验和。

如果只想要功能变化，这一版可以跳过。

## 改动

### 1. 生成式输入测试（`Id3StreamFuzzTest`，+1 例）

固定种子 `0x1D3F022`，15,000 例分五类语料：随机 3k / 结构化 4k / 良构 2k / 变异 4k /
截断 2k。断言四条：不抛、读取量有上界、两次调用同值、流式与缓冲两条路径不得给出**不同
数值**（允许流式更严格地返回 `null`）。

第 4 条是真正值得压的：这条路径上的分歧不会有异常、不会有日志，只有一个错音量。

结果：分歧 35 例，全部是「缓冲有值 / 流式 null」的截断类，**零例两路径给出不同数值**。

### 2. 两条可复跑取证脚本（`review/`）

`mutate.py` —— 17 个语义变异体逐条投放，真实编译、真实跑三个测试类。**17/17 killed**。
备份是字节级的：第一版用 `read_text/write_text`，在 Windows 上把换行交给平台翻译，还原校验
直接失败。现在用三个 blob 哈希相等（`git hash-object` / `git ls-files -s` / `HEAD:path`）
来证明源码没被污染。

`apk-diff.py` —— 逐条目比对压缩尺寸 + CRC + 解压后 SHA-256。本批的产物分析全靠它。

### 3. 分级台账（`review/2026-10-29-claim-ledger.md`）

A 真机读数 / B host 可复跑 / C 静态推断 / D 未测。**D 级不许进「全部通过」。**
本轮闭合 5 行（全 B）、未闭合 8 行（全 D）。

### 4. 一个被推翻的结论

原假设：手写用例覆盖不足，fuzz 能补上机器想不到的输入。

证伪：14 个变异体、两套断言（有/无 fuzz）都是 100%；再补 3 个只有生成式输入才可能触发的
边界变异（填充检测、循环边界、syncsafe 高位守卫），仍然都是 100%。

**结论：这条路径上 fuzz 的增量杀伤为 0。** 它的价值只剩一条——对 15,000 个生成输入证明
「不抛、不超读、确定性」，是崩溃安全性，不是覆盖补强。边界也要说清：17 个变异体是读过测试
之后挑的，100% 是这 17 个的下界，不是「任意 bug 都抓得住」。

由此产生的处置：不要再往这条路径加测试。真正没有变异覆盖的是 UI/动效
（`Motion.kt` / `CoverReflection.kt` / `MemoCache.kt`），那里只有「参数对不对」的断言，
没有「行为错了会不会被发现」的度量。

## 关于「整体 SHA-256 不可复现」

本机用同一份源码重新构建，185 个条目的压缩流**逐字节相同**（v2/v3 签名块也逐字节相同），
但整体 SHA-256 不同。原因已定位，不在本项目的可控范围内：

APK Signing Block 里有四个 part，其中 `0x504b4453`（DEPENDENCY_INFO_BLOCK）是 AGP 写入的
依赖树二进制，**用 Google 的公钥加密**，除 Google 外无人能读、也无人能验。它长度固定
（8,075 B）而内容随每次构建变化，且**不在 v2/v3 签名覆盖范围内**——两侧 v2/v3 的摘要
`4bf6d3c6…` / `a6d02d99…` 完全相同，只有这个块不同。它不参与安装校验。

因此本项目的「可复现」只能主张到条目层：同源码 → 185 条目 + 签名逐字节相同。要做到整体
SHA 相同，需要在 `android { dependenciesInfo { includeInApk = false } }` 关掉它——那会改变
包内容，**不在本批做**，留作下一批的候选。

## baseline.prof 的 7,124 字节：诚实的缺口

它随 versionCode 一起变，本机与 CI 结果一致，说明是确定性的、由输入驱动的。但
「26 字节的 dex 差异为什么会让 9,664 字节的 profile 重排七成」这件事，机理没有查明。
按指示停止追查。它不在执行路径上（是 ART 的编译提示），不影响正确性与安装，所以不被当作
阻断项，但也不写成「已解释」。
