本版把 1.0.47 之后的三条工作线合并发布：**索引水位线修复**、**解码器偏好**、**封面与缓冲链路的内存专项**。共 9 项改动，其中 2 项经真机验证，7 项未验证。

### 1. 索引水位线改用 `getGeneration()`

1.0.47 用 `COUNT(*)` + `MAX(DATE_MODIFIED)` 聚合做扫描水位线，真机验收发现 **MediaProvider 直接拒绝该聚合投影**，`runCatching` 返 null 后静默回落全量扫描——水位线等于没生效，而且多付了一次被拒绝的查询。

改用 `MediaStore.getGeneration()`：返回 `long`，跨重启稳定，一次 Binder 即可。聚合仅保留为 API 26–29 的兜底路径。tracks 与印章仍在**同一次 commit** 里写入。

真机验证：增、删双向各一次，二次启动都正确跳过了扫描。

### 2. 扫描 stamp 取值前移

旧代码在 `loadTracks()` **之后**取 stamp 保存，等于把快照标记成它可能并不包含的索引状态：

```
t0       stamp() → G1
t0..t1   loadTracks() 遍历中 ← 用户新增一首，索引变 G2
t1       save(fresh, stamp()) → 存下 G2
```

`fresh` 可能不含新增那首，但存的是 G2。下次启动 generation 相同 → 跳过扫描 → **那首歌直到手动刷新才出现**。

现在 stamp 在 `loadTracks()` 之前取一次，写入时复用同一值：既消掉一次重复 IPC（API 26–29 上那次是全表聚合，比读全库还贵），又能在索引读取期间变化时让下次启动自动重扫——自愈。

### 3. D1 解码器偏好

Android 17 起软件音频解码器可以进程内运行（`c2.android.inproc.*`）。在此之前每个解码缓冲要跨两次 Binder、付两次调度唤醒；高负载下队列化表现为欠载——听感是爆音或卡顿，不是错的采样。

`InProcessCodecSelector` 对平台列表**只重排、不重建**：平台列表本身已带能力过滤和 media3 依赖的逐 codec 规避项，未提升的条目保持原有相对顺序。

排序目标是 `硬件 → inproc → 其余软件`，不是无条件把 inproc 提到最前。硬件解码器始终在最前面——把软件解码器排到硬件前面，是把 DSP 的活换给 CPU，**增加**功耗而非节省。

真机验证：OPPO Android 17 上选中 `c2.android.inproc.aac.decoder`，初始化 17 ms。

### 4. API 26–28 封面采样缺口

1.0.47 的采样修复只覆盖了 `ArtworkBitmapLoader`（内嵌封面路径），漏掉 `ArtworkRepository.decodeBitmap` 的 `else` 分支——那里仍然 `MediaStore.Images.Media.getBitmap()` 全尺寸解码后再 `scale()`。

现在补成 bounds 预扫描 → `inSampleSize` 采样 → 等比缩放。以 1200 px albumart 生成 192 px 列表缩略图：

| | 峰值分配 |
|---|---|
| 改前 | 5.49 MB（全尺寸解码 + 缩放副本） |
| 改后 | 0.34 MB（300×300 采样 + 目标尺寸） |

**用户可感知的差异**：原实现 `bitmap.scale(size, size)` 把任意封面压成正方形，非 1:1 封面会变形。新实现保持宽高比，`CoverArt` 用 `ContentScale.Crop`，所以视觉上从「变形」变为「裁切」。

### 5. 位图缓存预算按堆动态计算

三层缓存原为硬编码 24 + 6 + 8 MB = 38 MB。192 MB 堆的机器上占 **19.8%**，越过「内存 1/8」惯例线，是 LMK 第一个回收的对象。

现在总预算 = `getMemoryClass() / 8`，钳制 16–48 MB，按 `10/16 : 2/16 : 1/16 : 3/16` 切成列表 / 播放页 / 背景 / 通知。

| `memoryClass` | 总预算 | 列表 | 播放页 | 背景 | 通知 |
|---|---|---|---|---|---|
| 192 MB | 24 MB | 15.0 | 3.0 | 1.5 | 4.5 |
| 256 MB | 32 MB | 20.0 | 4.0 | 2.0 | 6.0 |
| 384 MB+ | 48 MB（封顶） | 30.0 | 6.0 | 3.0 | 9.0 |

**代价**：192 MB 设备上列表缓存 24 → 15 MB，约 163 → 100 张封面。miss 后走本地 `loadThumbnail`（5–15 ms，异步），表现为滚动时偶见占位渐变。这是有意的内存优先。

未申请 `largeHeap`——`getMemoryClass()` 报的就是单进程上限，manifest 保持默认。

### 6. 播放页背景图缓存

`loadBackdrop` 原先每次调用都走一次 IPC + 96 px 解码，切歌与进出播放页都重来。现在加 1/16 预算的 LRU（96 px 约 36 KB/张，可存 40+ 张）与和另外两条路径一致的 `CompletableDeferred` 并发去重。

主导色扫描仍在每次进播放页重算——那属 UI 层职责，不在本次范围。

### 7. 补 `RUNNING_MODERATE` 档

原分级从 `RUNNING_LOW`(10) 起，缺 `RUNNING_MODERATE`(5) 这一级。补上后三层各减半。

**实现中踩过的一个坑**：`RUNNING_LOW = 10`、`RUNNING_MODERATE = 5`，两者都用 `>=` 判断，若把 MODERATE 分支放在 LOW 之前，`10 >= 5` 成立会**先命中更宽的分支**，1/8 的强裁剪永远不执行。分支按常量值降序排列（40 → 20 → 10 → 5），并在注释里写明顺序不可换。

减半不造成可见闪烁：`trimToSize` 淘汰最久未使用项，屏幕上的行和播放页封面恰是最近刚用过的，不会被动。

### 8. 小组件封面单次分配

`coverCache`（2 MB，按 `(albumId, radiusBucket)` 键）在 1.0.47 已存在，真正残留的是**首次渲染分配两张** 256×256 位图：先 `scale()` 一张，再在 `withRoundedCorners()` 里分配一张。

改为单张输出位图，用 `FILTER_BITMAP_FLAG` 把源图直接缩放绘制进 `SRC_IN` 圆角裁剪区。每曲瞬时分配 512 → 256 KB。

### 9. 解码缓冲池跨切歌保留

预读缓冲由 `DefaultAllocator` 池化，但 `DefaultLoadControl.Builder.build()` 默认传 `trimOnReset = true`：

```
DefaultAllocator.reset() → if (trimOnReset) setTargetBufferSize(0) → trim()
```

即**每次切歌池被整体释放**，下次重新分配 64 KB 块。FLAC 1411 kbps + 30 s 缓冲约 5.3 MB、82 个块。

改为 `trimOnReset = false` 的显式实例，并补回回收点：

| 时机 | 行为 |
|---|---|
| `onTrimMemory(>= BACKGROUND)` 且未播放 | `setTargetBufferSize(0)` |
| `onDestroy()`（`player.release()` 之后） | 同上 + 置空引用 |
| 下次 `onTracksSelected` | LoadControl 设回真实目标，池按需重建 |

`isPlaybackActive()` = `playWhenReady || isPlaying`，熄屏听歌时池不释放。段大小保持 64 KB 是硬约束——`trim()` 按整段计算，改尺寸会让字节账目与 LoadControl 的预期漂移。

**这一项是唯一没有实测支撑的调参**：改动生效的前提是「切歌确实产生了可观测的 GC 压力」，而这个数据尚未采集。真机验收项见下。

## 尚未验证（需真机，优先级从高到低）

1. **漏歌修复**（第 2 项）：扫描窗口内加歌，一次启动后应能自动重扫出现。
2. **后台内存**：浏览 300 首 → Home 键 → `dumpsys meminfo`，期望比 1.0.47 再降 10–14 MB。
3. **连续切歌 20 次**：对比 `GC_FOR_ALLOC` / `GC_CONCURRENT` 次数，验证第 9 项是否真的有收益。**没有这个数据，第 9 项应视为待定项**。
4. **熄屏播放 30 min** 的 PSS（确认缓冲池被保留而非泄漏）。
5. **暂停 → 后台 → `onTrimMemory`** 后的 PSS（预期回落 1–5 MB）。
6. **FLAC ↔ AAC 互切**：确认目标值下降时池正确收缩。
7. **滚动观感**：192 MB 堆设备上列表缓存缩到 15 MB 后的占位闪烁是否可接受。
8. **Widget 圆角**在 API 26–30 的渲染（`SRC_IN` 路径改造过）。
9. **播放页封面**：非 1:1 封面从变形变为裁切，确认视觉可接受。
10. **API 26–28 封面采样**：需旧版本模拟器 + 大尺寸 albumart，用 `dumpsys meminfo` 对比 PSS。

`adb shell am send-trim-memory com.milan.music RUNNING_MODERATE` 可直接触发第 7 项。

## 已知遗留

- **P3 聚合兜底路径仍在**：API 26–29 没有 `getGeneration()`，仍走聚合。该路径在拒绝聚合的 provider 上会静默回落全量扫描——老系统上是既有行为，未改。
- **`ArtworkBitmapLoader.onTrimMemory` 仍从 `RUNNING_LOW` 起**：无顺序陷阱，只是缺 MODERATE 档；通知位图预算仅约 3 MB，收益有限，保持现状。
- **与 1.0.47 一致**：P2（Haze 全尺寸离屏层）、M3（播放页 48 dp 模糊背板）、M4（3000+ 首撞 Binder 1 MB 事务上限）三项维持原判定；ReplayGain / EQ 未做；`store/screenshots/01-library.jpg` 与真实界面不一致，上架前必须重拍。
- **无自动化测试**：`src/test` 与 `src/androidTest` 均为空，本版 9 项改动全部依赖真机冒烟验证。

## 内容核验（为什么本包确实包含上面的改动）

### dex 字符串探针

R8 会重命名类与成员，但**序列化键名和字符串字面量不会变**，可直接在 `classes.dex` 里搜：

| 探针 | 归属 | 命中 |
|---|---|---|
| `index_generation` | 第 1 项（DataStore 键名） | **1** |
| `.inproc.` | 第 3 项（`IN_PROCESS_MARKER`） | **1** |
| `artwork` | 既有 | 4 |

`trimOnReset` 搜不到是正常的——它是构造参数名，R8 后不保留；该改动通过与 `DefaultAllocator` 的调用关系体现，不是字符串。

### 体积巧合，第三次出现

1.0.44 / 45 / 46 / 47 / 48 五个包的**压缩后**总字节数完全相同（2,477,875 B），但内容不同：

| 项 | 1.0.47 | 1.0.48 |
|---|---|---|
| `classes.dex` | 3,801,936 | 3,808,120（**+6,184**） |
| `baseline.prof` | 8,900 | 8,911 |
| `baseline.profm` | 1,046 | 1,040 |
| 解压后总计 | 4,368,542 | 4,374,731（**+6,189**） |
| 条目数 | 193 | 194 |
| SHA-256 | `d9cf6f39…` | `af27abfe…` |

deflate 把 6 KB 的增量吸收掉了。**总字节数不能作为「是否重建」的判断依据，SHA-256 才能**——这条结论已连续三个版本成立。
