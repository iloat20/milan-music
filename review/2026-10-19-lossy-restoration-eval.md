# 有损音频修复与高解析动态重制评估

| 项 | 值 |
|---|---|
| 评估对象 | 基于 DSP 的有损修复（谐波重建 / 立体声细节 / 过采样 + 动态扩展） |
| 本项目 | milan-music 1.0.47 · Media3 1.11.1 · 已启用 offload · minSdk 26 |
| 性质 | 只读评估，未改任何代码 |
| 结论 | **技术描述成立但定性有偏差**：这是"合成"不是"恢复"，且代价是**关掉 offload**——本项目当前最大的功耗优化。不建议做完整套件 |

---

## 1. 先说定性：这四件事在数学上分别是什么

| 你的说法 | 真实技术 | 能不能做到 | 性质 |
|---|---|---|---|
| 重建丢失的谐波 | 频带扩展 / Spectral Band Replication（SBR） | 能 | **合成**（inference），不是恢复 |
| 重建丢失的立体声细节 | stereo widening / M-S 处理 | 只能加宽 | 数学上不可恢复，见 §2.2 |
| 过采样 | 插值 + 抗镜像滤波 | 能 | 不增加任何信息 |
| 动态扩展恢复冲击力 | downward expander + limiter | 能 | 效果器，不是修复 |
| 逐曲目损伤程度检测 | 频谱截止点检测（FFT 找码率截断） | 能 | 需要离线预分析 |

用一句话概括：**有损编码丢掉的信息不可逆，所谓"修复"是在缺失的位置合成"听起来合理"的内容。** 这不是贬低——Sony 的 DSEE 做得好，主观上确实明显；但把它叫"修复"会让用户以为自己在拿回原始信号。

---

## 2. 三处需要修正的描述

### 2.1 "基于 DSP 而非黑盒 AI"

和现役产品对不上。Sony 的技术族分三代：

- **DSEE / DSEE HX（2009 / 2013）** —— 纯 DSP，SBR + 插值 + 动态增强，输出最高 24-bit/192 kHz
- **DSEE Extreme（2020）** —— **edge AI**，用 Sony Music 的母带库训练，在 WH-1000XM4/XM5 的 Integrated Processor V1 上跑
- **DSEE Ultimate（2023）** —— AI，支持有线与无线，最高 32-bit/192 kHz

也就是说，"发烧级播放器正在集成的差异化功能"里最有名的那一个，恰恰是**黑盒 AI**。纯 DSP 派（SBR + 包络跟随）是上一代做法，优点是行为可预测、不需要训练数据。

而且这个能力**无法以 app 形式获得**：DSEE 是烧进 DAC/处理芯片的专有功能，官方明确说它只存在于 Sony 自家硬件线。第三方播放器不可能集成它，只能自己重写一套。

### 2.2 "重建丢失的立体声细节"——这条在信息论上不成立

有损编码的 joint stereo / M-S 编码里，side 通道是**被量化过**的。量化掉的比特已经不在文件里，任何算法都无法把它算回来。

实际能做的只有三种，都不是"重建"：

1. **stereo widening**（相位/延迟/中侧比例调整）—— 听起来更宽，但相位失真，单声道下会抵消
2. **对 side 通道做谐波合成** —— 让声场"有内容感"，内容是合成的
3. **reverb 尾巴延长** —— 把混响拖尾补长，制造空间感

效果确实存在，但归类到"效果器"比"修复"准确。

### 2.3 "在不削波的前提下恢复冲击力"

动态扩展（expander）会把**整个动态范围**往上抬，包括底噪。对 128 kbps 的 MP3，这意味着把编码噪声一起放大——听感上"冲击力恢复"和"底噪变明显"是同一件事的两面。

Sony 自己的说明里有一条值得注意：这类处理**对未压缩或高比特率源无效，甚至可能造成过度处理**。也就是说它的适用面是"低码率文件"，而我们刚做的 bit-perfect 恰恰是给高解析源的。两个功能的目标人群相反。

## 3. 对本项目的真实代价

### 3.1 硬冲突：启用任何 AudioProcessor 都必须关掉 offload

这一条是决定性的，代码里已经写明了（`PlaybackService.kt:83-85`）：

> offload bypasses ExoPlayer's audio post-processing, so any future equalizer or speed control must switch the mode to DISABLED while it is active

机制上：offload 把编码帧原样交给 DSP，绕开整个 `AudioProcessorChain`；一旦链上有处理器需要 PCM，就只能走普通 PCM 输出路径，解码回到 CPU、混音回到 AudioFlinger。

**1.0.46 里启用 offload 是这批优化中最大的单项功耗收益。** 做实时 DSP 修复等于把它交回去，换来一个主观的听感提升。这是拿确定性换不确定性，方向不对。

### 3.2 计算开销（可以量化）

| 项 | 数值 |
|---|---|
| PCM 流量（48 kHz / 立体声 / float32） | 384 KB/s |
| 谐波合成（FFT 1024 + overlap-add，hop 512） | 约 94 次 FFT/秒 |
| 手机 CPU 上的实际占用 | 个位数 % —— 不是瓶颈 |

所以瓶颈不是算力，是 §3.1 的 offload 冲突和 §3.3 的电量账。

### 3.3 要做的模块清单

1. **损伤检测**：FFT 看频谱截止点（128 kbps MP3 通常 16 kHz、320 kbps 约 20 kHz），得出"带宽上限"与"是否 joint stereo"
2. **预分析缓存**：每首歌分析一次，结果落盘（否则每次播放都要重算）
3. **SBR 合成器**：从截止点下方的幸存频带生成谐波，包络跟随原始滚降
4. **瞬态恢复**：检测被编码抹平的 attack，做局部增益整形
5. **动态扩展 + limiter**：需要严格防止二次削波
6. **UI**：强度档位 + 逐曲目开关（无损文件上必须自动关闭）

这是**一个新子系统**，不是给现有链路加开关。参照 §3.1，它还会把 offload 的收益吃掉。

## 4. 三条路

### A. 只做检测，不改声音（建议先做这个）

用 FFT 判断每首曲目的频谱截止点与预估码率，在 UI 上显示（例如"带宽 16 kHz · 疑似 128 kbps 转码"）。

- 零风险：不碰播放路径、不改 offload、不影响任何已有验证项
- 有真实信息价值：能告诉用户"你收藏的这批文件其实是低码率转录的"，这比"帮你修补"更诚实，也更有用
- 代价：约 100 行 + 一次离线分析 + 缓存

### B. 温和 DSP（只在有明确用户诉求时做）

只做谐波合成 + 瞬态恢复，不做动态扩展（底噪放大的风险最大）。必须：

- 默认关闭，纯手动开关
- 无损源自动旁路
- 开启时明确提示"将关闭音频卸载，功耗会上升"

### C. 完整套件（含立体声扩展与动态重制）

不建议。它同时牺牲 offload、放大底噪、引入相位问题，且与 bit-perfect 的产品方向相反。

## 6. 结论

技术描述本身没有错，SBR + 瞬态恢复 + 过采样 + 动态扩展确实是这套东西的完整配方，也确实能在低码率文件上听出差别。

但把它放进 milan-music 有三个问题：**第一**，代价是关掉 offload，拿确定的功耗换主观的听感；**第二**，"修复"这个词会误导用户以为信息可以取回；**第三**，它和刚评估的 bit-perfect 是相反的产品方向，同时做会让"这个播放器到底想忠实还是想好听"变得说不清。

建议只做 **A（检测 + 展示）**。它不改声音，不会和任何已做的优化打架，而且回答的是同一类问题——"我的文件到底有多好"——只是用诚实的答案代替合成的答案。
