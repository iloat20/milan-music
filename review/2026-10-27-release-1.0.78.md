# Release 1.0.78 (vc 79, b79)

本批把审查清单里剩下的 P2 与 P3 逐条落地。六条改动里只有一条能在 JVM 里断言（见
"门禁"末段），其余五条的观测面都在 Android 运行时 —— 这一点写在最前面，不靠门禁
数量充数。

基线：AGP 9.4.1 / Kotlin 2.4.21 / Gradle 9.8.2 / compileSdk 37 / minSdk 26。

## 一 · 通知封面并发重复解码（P2）

`ArtworkBitmapLoader.loadBitmap` 的缓存检查在 `executor.submit` **之前**，`Callable`
内部不复查。换曲时通知栏与锁屏几乎同时请求同一张 art，两次都 miss、两次都入队；执行器
是单线程，于是它们串行跑完两次完整解码（512 px，约 10 ms + 1 MB 瞬时分配）。

改法是在 `Callable` 开头补一次 `cache.get(uri)`。执行器单线程意味着第二个任务跑到时
第一个已经填好缓存，这次复查把第二次解码变成一次 Map 命中。

## 二 · 倒影之外的死代码：`shade()` 的纯黑分支（P3）

`shade(color, minLuminance, maxLuminance)` 里有一段：

```kotlin
if (luminance < 1e-5f) return Color(neutral, neutral, neutral)   // 永不执行
```

它上面一句已经是 `if (luminance <= ceiling) return color`，而纯黑亮度是 0、
`ceiling = max(minLuminance, maxLuminance)` 不可能小于 0 —— 这段代码**永远走不到**。
更糟的是它的注释承诺"纯黑给中性色"，这个行为从未发生过。

两个调用点（`paletteOf` 的 `bottom` 与 `top`）传的 `minLuminance` 都是 `0f`，所以这个
参数本身也是死参数。删掉分支与参数，签名收成 `shade(color, maxLuminance)`。

**这是行为等价的改动**，逐条核对过：`min=0` 时 `ceiling == max`；`ceiling == 0` 且颜色
非黑时两边都算 `factor = 0 → 变黑`；`ceiling == 0` 且颜色是纯黑时两边都原样返回。
纯黑封面真正的兜底在上游 —— `bandColorOf` 返回 `null`，`paletteOf` 整页退回
`FallbackPalette`（`blackCoverFallsBackInsteadOfReturningBlack` 已覆盖）。

## 三 · 当前曲目的索引兜底（P3）

```kotlin
val currentTrack = mediaItem?.let { resolve(it) }
    ?: queue.getOrNull(mediaController.currentMediaItemIndex)   // 删掉
```

`currentMediaItemIndex` 是 **shuffle 之后**的 timeline 位置，不是传给 `setMediaItems`
那个列表的下标 —— shuffle 开启时它指向另一首歌。它还会在"没有当前项"的窗口里触发
（`setMediaItems` 之后、会话真正产出该项之前），那时下标毫无意义，`queue[0]` 也未必是
起始曲。两种情况下显示的都是**与正在播放的不是同一首**的歌。

删掉兜底之后，解析不出来时 `_state.update` 保留上一首 —— 陈旧，但不会错。顺带删掉
`queue` 字段：它是这个兜底唯一读者，保留下来就是"写而不用"的第二份队列真相。

## 四 · 收藏按钮的描述被读两遍（P3）

`contentDescription` 原本写在 `AnimatedContent` 内部的 `Icon` 上。切换的瞬间新旧两个
图标同时存在于组合中，TalkBack 会把两句连着读（"喜欢 取消喜欢"）。

描述提到外框：`Box(… .semantics { contentDescription = description })`，图标改
`contentDescription = null`。锚在一处，任何时刻只有一句，且随 `isFavorite` 换。

## 五 · 进度条的无障碍描述硬编码分隔符（P3）

`stateDescription = "$pos / $dur"` 里的 `" / "` 直接写在代码里。搬到
`R.string.progress_state_description`（`%1$s / %2$s`）。

注意 `stringResource` 在 `semantics { }` 这类普通 lambda 里取不到，所以必须在组合期
先 hoist 成局部变量再传进去。

## 六 · 快照 ticker 在暂停时仍然每十五秒醒一次（P3）

`startSnapshotTicker()` 在 `onCreate` 无条件启动，循环体内再 `if (player.isPlaying)`
判断。服务被系统留着但一直暂停时，等于每十五秒唤醒一次主线程去问一个已知为 false 的
状态。

改成由 `onIsPlayingChanged` 启停：播 → `startSnapshotTicker()`，停 → 新加的
`stopSnapshotTicker()`；`onCreate` 只在**已经在播**时才启动（暂停着创建服务不该凭空
开循环）；`onDestroy` 改走 `stopSnapshotTicker()`。启动加了 `positionJob?.isActive`
幂等判据 —— 切歌缓冲会让 `isPlaying` 连续报两次 true，重复启动会留下两个循环、写入
频率翻倍，而 `snapshotWriteLock` 只会让它们排队，不会互相抵消。
